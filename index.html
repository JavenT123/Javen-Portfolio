Network security · home lab · Raspberry Pi

Home Network Security Stack

Designed and deployed a multi-layer network security system on a Raspberry Pi from scratch — DNS filtering, recursive resolution, intrusion detection, VPN access, and system hardening. Built in deliberate phases with security controls enforced before any service was exposed. Running 24/7 in production.

Pi-holeUnboundSuricata IDSWireGuardOpenVPNUFWFail2banDuckDNSLinuxDNSSEC

Architecture

Raspberry Pi 4 (2GB) running Raspberry Pi OS Lite 64-bit at static IP 10.0.0.10. All network devices route DNS through Pi-hole via router-level configuration — no per-device setup needed. Pi-hole forwards allowed queries to Unbound on localhost port 5335 for fully recursive resolution with no upstream DNS provider. Every query resolved directly from root servers — Google, Cloudflare, and the ISP never see what's being looked up.

Components & what each one does

  • OS Hardening — SSH disabled entirely. Raspberry Pi Connect handles remote access via outbound relay — no inbound port needed, eliminating port 22 attack surface completely.
  • UFW Firewall — Default-deny incoming. Subnet-restricted rules — ports 53, 67, 80 only reachable from 10.0.0.0/24. Principle of least privilege at the network level.
  • Fail2ban — Custom jail for Pi-hole admin interface. UFW as banaction for consistency. Custom regex filter. 1-day ban time, 45-minute detection window to catch slow brute force attempts.
  • Unbound — Fully recursive DNS resolver on port 5335. Queries go directly to root DNS servers. DNSSEC validation enabled and confirmed working. DNS rebinding attack protection via private-address directives.
  • Pi-hole — Network-wide DNS sinkhole. All devices protected automatically via router DNS setting. Custom blocklists on top of defaults.
  • WireGuard VPN — Self-hosted on port 51820. DuckDNS (toppick.duckdns.org) provides stable hostname. VPN clients use Pi-hole for DNS — ad blocking works away from home.
  • OpenVPN — Fallback VPN on TCP port 443. Port 443 = HTTPS — can't be blocked without breaking all web traffic. Works through every firewall including corporate networks.
  • Suricata IDS — Passive intrusion detection watching eth0. 52,000+ rules loaded. Detected real traffic patterns within hours of deployment including Discord usage and STUN traffic.

Key design decisions

  • SSH disabled — Raspberry Pi Connect uses outbound relay, no inbound port needed
  • UFW subnet-restricted — even open ports only reachable from trusted local devices
  • Firewall configured before any service installed — never expose before controls in place
  • Unbound over upstream provider — no third party ever sees DNS queries
  • OpenVPN on TCP 443 not UDP 1194 — guaranteed to work through all firewalls
  • ECS disabled — EDNS Client Subnet leaks home IP to authoritative servers
  • Reverted DoT rather than running broken forwarding — stable recursive DNS more valuable than unreliable encryption layer

Real challenges solved

Challenge 1
Fail2ban crashed — regex missing HOST capture group
Diagnosed using fail2ban-client -vvv. Identified "No failure-id group" error. Rewrote failregex to include <HOST> tag.
Fail2ban must know which IP to ban — <HOST> is mandatory in every filter.
Challenge 2
Two Unbound instances running — wrong port conflict
ss -tulpn showed two PIDs on ports 53 and 5335. Killed old instance, new config took over correctly.
Always verify what's actually listening after config changes — don't assume restart worked.
Challenge 3
DNS-over-TLS returning SERVFAIL despite correct config
Confirmed ISP blocks port 853. Port 443 connects to Quad9 but Unbound forward zone returned persistent SERVFAIL. Made deliberate decision to maintain stable recursive resolution. Identified Stubby as the correct tool for DoT — planned as next enhancement.
Recognize when a tool isn't the right fit and use the right one rather than forcing a broken solution.
Challenge 4
WireGuard blocking all 10.0.0.x local traffic on desktop
route print on Windows showed WireGuard routing all 10.0.0.x through VPN tunnel instead of local network. Deactivated WireGuard — routing restored immediately.
Always check active VPN connections when troubleshooting connectivity — VPN routes override local routing tables.
Challenge 5
wlan0 causing routing conflicts — all external pings failing
ip route show revealed wlan0 got 10.0.0.253 from ISP DHCP, creating two default routes on same subnet. Disabled wlan0 permanently via nmcli autoconnect no.
Multiple interfaces on same subnet create routing ambiguity. ip route show is the diagnostic tool.

What I learned

The most valuable lesson was learning to think in layers. UFW controls what gets in. Fail2ban handles repeat offenders. Pi-hole filters at the DNS layer. Unbound eliminates third-party visibility. Suricata watches everything that made it through all of that. Real security isn't one strong wall — it's many layers each catching what the others miss. That principle applies whether you're securing a Raspberry Pi or a Fortune 500 enterprise network.
